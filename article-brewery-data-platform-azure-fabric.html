Building a brewery data platform on Microsoft Azure and Microsoft Fabric

What is a brewery data platform on Azure and Fabric?

A brewery data platform is the place where every system's records about a batch end up joined: brewhouse, cellar, packaging, lab, maintenance, ERP, sales and duty. On Microsoft Azure and Microsoft Fabric, that place is OneLake, the single data lake that every Fabric engine reads directly. Spark notebooks, the SQL endpoint, Power BI and the real-time engine all work on the same copy instead of each keeping its own.

The reason this matters in a brewery is simple. The questions that cost money cross systems. Beer loss needs brewhouse cast volume, cellar transfers, packaging counts and the duty register. Fermentation time needs historian readings, yeast records and the lab. A platform that keeps those in separate tools forces someone to rebuild the join in Excel every month. I have been that someone. The spreadsheet was called LOSSES_FINAL_v3. It was the most trusted number in the building because nobody else could reproduce it.

The goal of the platform is to make that join once, write down the rules and let everyone read the same answer.

How brewery data gets into Microsoft Fabric

Fabric gives a brewery several routes in. The right one depends on the source. Choosing the route per source, rather than forcing everything through one pipeline, is most of the design work.

Brewery sourceTypical systemRoute into Fabric
ERP: recipes, goods receipts, costs, stockSQL Server, Azure SQL, Dynamics 365Database mirroring into Delta tables, or Link to Fabric for Dataverse
Process historian and PLC tagsOPC UA servers, Azure IoT Hub, Event HubsEventstream into an Eventhouse for time-series queries
Lab and LIMS exportsCSV or Excel dropsShortcut with file transformation into Delta tables
Brew sheets and SOPsSharePoint or OneDriveOneDrive and SharePoint shortcuts
Data held on other cloudsAmazon S3, Google Cloud StorageShortcuts that read in place without copying
Sales and distributor filesPortals, email attachments, CSVPipelines or dataflows on a schedule

Shortcuts deserve a word. A shortcut is a pointer in OneLake to data stored somewhere else, so the data appears local but is not copied. When the source updates, the change is visible through the shortcut. For a brewery that already keeps lab files in one place and ERP extracts in another, this means the platform can start reading before anyone migrates anything.

Two practical points save weeks. First, decide the time zone for every timestamp on day one, because historians often log UTC while brew sheets use local time. A shift boundary error then moves readings into the wrong batch. Second, land data in the brewery's units with the unit in the column name, such as volume_hl or gravity_plato. Converting later is easy. Guessing later which column was litres is not.

A worked example: why historian data needs its own engine

Say a brewery logs 400 historian tags: fermenter temperatures and pressures, glycol supply and return, CIP conductivity, compressor currents, filler speeds. Each tag records once a second.

Historian readings per dayrows per day = tags x seconds per day = 400 x 86,400 = 34,560,000

Over a year that is 34,560,000 x 365 = 12,614,400,000 readings.

Twelve and a half billion rows a year is not a problem for the right engine. It is a problem if someone imports it into a Power BI model or a spreadsheet. In Fabric the time-series data belongs in an Eventhouse, which is built for high-volume event and telemetry analysis and is queried with KQL. Its Real-Time Dashboards refresh as data arrives. Activator can send a notification when a rule fires, such as a fermenter running 1 °C above its profile for 30 minutes.

The batch record then holds the summary, not the raw stream: the time at each gravity stage, the peak temperature, the minutes out of profile. Cellar and quality teams read the summary. The raw readings stay in the Eventhouse for whoever needs to look closer.

Shaping the data: one batch record and a governed model

Landing data is the easy half. The hard half is the batch record: one row per brew, with the brewhouse, cellar, packaging and lab facts joined by a key everyone agrees on. Most breweries have three keys, the brew number, the fermentation number on the tank and the packaging lot. Mapping them once, including blends and split packaging runs, is the most valuable work on the whole platform.

  • Bronze: raw copies or shortcuts, exactly as the source wrote them.
  • Silver: cleaned tables with consistent units, times in one time zone and batch keys mapped.
  • Gold: the batch record, loss by stage, cost per hectolitre and the other measures people actually ask for, each with a written definition.

Power BI reads the gold layer through a semantic model in Direct Lake mode, which reads Delta tables in OneLake without a scheduled import. The same governed model is what a Fabric data agent queries when someone asks a question in plain English, so the dashboard and the chat answer come from one definition of packaged volume, not two.

Machine learning sits on the same layers. A fermentation time model trains on silver tables of gravity readings joined to yeast generation and pitch rate, in a Fabric notebook and writes its forecast back as a column in the batch record. The cellar manager never opens the notebook. They see a predicted terminal date next to each tank in the report they already use. Keeping models inside the platform, rather than in a separate tool with its own copy of the data, means the forecast is always built on the same definitions as the report beside it.

Security, tenancy and what good looks like

On Fabric the data stays in the brewery's own Microsoft tenant, under the brewery's own Microsoft Entra identities. OneLake security can apply row-level and column-level rules that hold across engines, so a site brewer sees their own site's tanks whether they use a report or a notebook. Cost data can be hidden from roles that do not need it. Setting these rules in OneLake rather than only in each report is what stops a clever user reading round them.

Build it in stages. Start with two sources that answer one question, such as brewhouse records and packaging counts for beer loss. Prove the batch key on those. Add the lab next, then the historian summaries, then cost. Each stage should end with a number the plant uses in a meeting. A platform that lands twenty sources before anyone uses one number is a storage bill, not a data platform.

A good brewery data platform on Azure and Fabric looks dull from the outside. Numbers agree between the cellar report and the finance pack. A new question takes days, not a project. The historian, the ERP and the lab are still the systems of record. Nobody had to replace them. When it goes wrong, it is usually because the batch key was skipped to get a dashboard out early.

Questions people ask

Is Microsoft Fabric suitable for a brewery?

Yes, for breweries that want ERP, historian, lab and sales data in one place. Fabric covers batch data through lakehouses and warehouses, time-series data through Eventhouse and reporting through Power BI, all on one copy of the data in OneLake.

How does historian data get into Microsoft Fabric?

Usually through an Eventstream from a source such as Azure IoT Hub, Event Hubs or Kafka into an Eventhouse, where it is queried with KQL. A summary per batch then moves into the lakehouse for reporting.

Do we have to replace our ERP or LIMS to use Fabric?

No. Fabric reads from existing systems through mirroring, shortcuts, pipelines and file transformations. The ERP, historian and LIMS stay the systems of record.

Where is the brewery's data stored on Fabric?

In OneLake inside the brewery's own Microsoft tenant, secured with its own Microsoft Entra identities. Row-level and column-level rules can be set in OneLake security so they apply across Fabric engines.
