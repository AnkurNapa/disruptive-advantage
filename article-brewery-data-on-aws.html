How to approach brewery data and AI on AWS if you already run there

If your brewery already runs on AWS, there is no reason to move to get value from its data. The hard work is the same on every cloud: one batch record and agreed definitions.

Should a brewery on AWS move clouds to do data and AI?

No. A brewery that already runs its ERP, historian exports or e-commerce on Amazon Web Services can build its brewery data and AI work on AWS. The cloud is rarely the reason a brewery's numbers disagree. The reason is that the brew number in the brewhouse log, the tank number in the cellar and the lot code on the filler were never mapped to each other. That problem travels with you to any provider.

I will be plain about where I stand. Beer365 runs on Microsoft Azure and Microsoft Fabric inside the brewery's own Microsoft tenant. That does not make AWS the wrong place for a brewery's data. It means this article covers two things: how a brewery on AWS should approach its own data and AI, then how a Fabric-based tool can read that data where it sits.

How a brewery should approach data and AI on AWS

The building blocks on AWS map cleanly onto a brewery. These are the services I would look at first, described the way AWS documents them.

Brewery needAWS serviceWhat it does for the brewery
One place for raw and shaped dataAmazon S3Object storage for ERP extracts, lab files, historian exports and the shaped batch tables, ideally in an open table format such as Delta or Iceberg
Equipment and process data from the floorAWS IoT SiteWiseCollects, stores, organises and monitors industrial equipment data. Asset models describe fermenters, compressors and fillers. Its edge gateway reads OPC UA servers on site
Plant metricsAWS IoT SiteWiseComputes metrics such as overall equipment effectiveness and mean time between failures from the asset data
GenAI over batch records and SOPsAmazon Bedrock Knowledge BasesRetrieval augmented generation over your documents, with citations so the source can be checked

AWS IoT SiteWise is worth a closer look for the floor. Its documentation lists food and beverage as a use case, with examples like monitoring refrigeration across sites. It keeps recent equipment data in a hot tier for live monitoring, moves older data to a warm tier for analysis and can put cold history in your own S3 bucket. A single SiteWise Edge gateway can connect up to 100 OPC UA servers, which covers most breweries' automation estate.

Model the plant before you collect it. A SiteWise asset model for a fermenter should carry the tags that matter to a brewer: jacket temperature, top and bottom probes, pressure, the gravity readings from the lab. If the asset hierarchy mirrors the actual cellar, the cellar manager can find tank 12 without learning a tag naming scheme written in 2009.

Pick the first use on AWS the same way you would anywhere: by the money. For a brewery running ammonia refrigeration around the clock, SiteWise alarms on compressor discharge temperature and motor current are a cheap first step, because the data already exists in the PLC and the cost of a failed compressor in July is easy to write down. For a brewery short of fermenter space, a fermentation time forecast trained on gravity readings in S3 frees tank days. For a quality team buried in paperwork, a Bedrock knowledge base over deviation reports and SOPs gives them search with sources. Each of these can be built entirely on AWS by a team that knows it.

The part no AWS service does for you

None of those services know that a brewery packages one fermentation into three SKUs over two days, or that a blend draws from two tanks with different brew numbers. That mapping is brewery knowledge. On AWS, as anywhere, it becomes a batch record: one row per brew joining brewhouse, cellar, packaging and lab, kept as a table in S3 with a written definition for each measure.

  • Brewed, packaged and sold volume must be three separate measures with names, or every loss figure will be argued about.
  • Times must be in one time zone. Historians often log UTC while brew sheets are in local time.
  • Units must be explicit: hectolitres or litres, °Plato or specific gravity, never both in one column.
  • Calibration records must sit beside the sensor data, because a probe reading 0.8 °C high will train a model to be wrong.

With that record in place, Bedrock Knowledge Bases can answer questions over batch records and SOPs with citations. Equipment models can train on SiteWise history joined to maintenance logs. Without it, both will produce confident answers about the wrong batch.

Whichever services you choose, keep the shaped tables in an open format such as Delta or Iceberg in S3. They are still ordinary files in S3. The format keeps the batch record readable by other engines later, including Microsoft Fabric, without an export job sitting in the middle that someone has to maintain.

Can Microsoft Fabric read brewery data stored on AWS?

Yes. Microsoft Fabric supports OneLake shortcuts to Amazon S3. A shortcut is a pointer, so the data stays in your bucket and is not copied. Microsoft documents S3 shortcuts as read-only access to data in any file format. If the data is a Delta table, it can appear as a table in a Fabric lakehouse, queryable through Spark and the SQL endpoint.

A few details matter for a brewery's security and cloud bill. Fabric can cache files read through S3 shortcuts, with a retention period you set between 1 and 28 days, to reduce egress costs from cross-cloud reads. Files larger than 1 GB are not cached. For buckets behind a firewall or VPC, Fabric can connect through an on-premises data gateway. Microsoft also documents Microsoft Entra service principal authentication for S3 shortcuts, which avoids managing AWS access keys.

To be clear about the trade-off: a brewery happy on AWS can build all of this on AWS. Reading S3 from Fabric makes sense when the brewery also uses Power BI or Microsoft 365, when a group company standardises on Microsoft or when a Fabric-based tool needs to work on the data without anyone migrating it. Cross-cloud reads still have a network cost on the AWS side, so the shape of what crosses matters, as the next example shows.

A worked example: move summaries across clouds, not streams

Say a brewery's historian exports to S3 come to 2 GB a day of raw tag readings. The batch summary for the same day, with gravity stages, peak temperatures and minutes out of profile per tank, is 20 MB.

Share of bytes read across cloudssummary / raw = 20 MB / 2,000 MB = 1 percent

Read the summary through the shortcut. Leave the raw stream on AWS for engineers who need it.

Pointing a cross-cloud report at the summary instead of the raw stream means reading one hundredth of the data every refresh. The shaping happens on AWS, next to the data. Only the shaped table crosses. That is good practice whichever direction the data flows.

Beer365 can work this way for a brewery on AWS. It reads the shaped tables in S3 through Fabric shortcuts, builds the one batch record inside the brewery's own Microsoft tenant and answers questions with the batch records cited. The data stays where the brewery put it.

Questions people ask

Can a brewery use AWS for data and AI?

Yes. Amazon S3 can hold brewery data, AWS IoT SiteWise can collect and model equipment data from the floor and Amazon Bedrock Knowledge Bases can answer questions over batch records with citations. The brewery still has to build the batch record and agree definitions.

Does Microsoft Fabric work with Amazon S3?

Yes. Fabric supports OneLake shortcuts to Amazon S3 that give read-only access to bucket data without copying it. Fabric can cache shortcut files for 1 to 28 days to reduce egress. It can also reach network-restricted buckets through an on-premises data gateway.

Do we need to move our brewery data from AWS to Azure to use Beer365?

No. Beer365 runs on Azure and Microsoft Fabric but can read data in Amazon S3 through OneLake shortcuts, which point at the data without copying it.

What is AWS IoT SiteWise used for in food and beverage?

AWS documents it for collecting, storing, organising and monitoring industrial equipment data, including food and beverage examples such as refrigeration monitoring across sites. It also computes metrics such as OEE and mean time between failures.
